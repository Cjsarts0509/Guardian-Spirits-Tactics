# 방장 호스팅과 자동 이전

## 현재 구현

새 웹 화면에서 만든 방은 `hosting: player`로 시작한다. 방장의 브라우저 Web Worker가 기존 순수 규칙 엔진과 기본 AI를 실행한다. 서버는 대기실·접속자 명단·처음 정체 배정·호스트 선정·입력 번호 부여·체크포인트 저장·메시지 중계·수신자별 뷰 필터링·종료 기록을 맡는다. 이 방의 서버 틱은 `advance`/봇 정책을 실행하지 않는다.

이는 게임 계산을 방장에게 옮긴 중계형 구조다. 모든 게임 메시지가 기존 WebSocket 서버를 거치며 직접 WebRTC P2P 연결은 구현하지 않았다. 서버 CPU 부하는 일부 분산되지만 중계·JSON 처리·뷰 생성 비용과 서버 연결 의존성은 남는다. 속도/수용량 개선은 별도 실측 대상이다.

기존 API 클라이언트가 hosting을 지정하지 않으면 서버 계산 방을 만든다. 기존 부하 진단과 AI 리그는 계속 그 경로를 사용하며 새 방장 호스팅의 성능 검증으로 재사용하지 않는다. 새 hello의 `hostCapable`을 보낸 클라이언트만 진행 중 계산 호스트로 선정한다.

## 확정과 복구

서버가 사람의 행동에 연속 입력 번호를 붙인다. 방장은 번호 순서로 처리한 뒤 상태·AI 기억·RNG·행동 기록·처리 번호·행동 결과를 한 프레임으로 제출한다. 서버가 현재 호스트/권한 epoch/연속 프레임 번호와 상태 형식을 검사하고 저장한 뒤 ACK·행동 결과·각자의 뷰를 보낸다. 워커는 ACK를 기다리는 동안 다음 프레임을 제출하지 않는다.

연결 종료나 명시적 퇴장 시 첫 번째 접속 중인 호스팅 지원 사용자에게 즉시 이전한다. 살아 있거나 관전 중인 사용자 모두 가능하며 봇·자리 비움·구버전 화면은 제외한다. 연결은 살아 있지만 프레임이8초 동안 없으면 이전하고 실패한 호스트는30초간 재선정하지 않는다. 원래 방장이 돌아와도 현재 호스트를 빼앗지 않는다. 같은 세션의 새 연결로 교체되는 경우에는 새 epoch를 발급한다.

새 호스트는 마지막 **서버 확정** 체크포인트를 복원한다. 확정 전 봇 판단은 버려질 수 있지만 사람의 미확정 입력은 다시 전달한다. 처리 번호로 재전송의 중복 적용을 막는다. 이전 epoch의 프레임은 거절한다. AI의 Map/Set 관찰·스킬/쿨다운 기억·계획·RNG는 직렬화한다. 파생 믿음 캐시는 전송에서 제외하고 새 호스트가 다시 계산한다. 서버는 AI 기억을 Map/Set으로 복원하지 않고 Map/Set을 복원하지 않은 JSON 구조로 보관한다. ACK된 프레임 번호를 기준으로 기억의 변경/추가/삭제만 적용하고, 최근64개 관측 이력의 앞 이동은 기존 항목을 재사용한다. 변경분이 더 크면 전체 기억을 전송한다. 잘못된 기준/배열/깊이는 확정하지 않으며 기존 호스트 이전 경로가 마지막 확정 전체 기억을 복구한다. 확정 로그와 행동 기록은 ACK된 길이를 기준으로 추가분만 전송하고, 서버가 기준 길이를 검사해 전체 기록을 합친다. 호스트 이전 때 전체 체크포인트를 생성한다.

게임 시간은 마지막 체크포인트의 시각에서 새 호스트의 단조 시계로 이어간다. 호스트가 없으면 시간·AI 계산이 정지하며 화면에 연결 대기를 표시한다. 새로고침/재접속 후 접속자가 있으면 복구한다. 모두 접속을 끊으면 AI 전용 판도 계속 돌지 않는다. 호스트 없는 방은10분 뒤 정리한다. 서버 재시작 후 복구는 아직 지원하지 않는다.

## 신뢰와 크기

일반 참가자는 기존 자기 뷰·수신 가능한 이벤트만 받는다. 전체 체크포인트는 지정 호스트에게만 전달한다. 방장/후임 방장이 개발자 도구나 변조 코드로 전체 정체를 보거나 결과를 조작할 수 있는 캐주얼 호스팅 모델이다. 서버의 스키마 검사·호스트 권한 검사는 입력의 형태와 전달 권한을 확인하며 호스트의 정직성을 증명하지 않는다.

체크포인트 문자열은8MiB, WebSocket 전체 프레임은9MiB 한도다. 일반 요청은 기존16KiB 한도를 유지한다. 이탈/퇴장 입력을 제외한 미확정 행동 대기는256개로 제한한다. 게임 상태와 지속 AI 기억은 매 틱 전송하지만 확정 로그·행동 기록의 중복 전송은 제거했다. 8MiB는 수신 체크포인트 문자열 한도이며 누적 기록을 합친 이전용 전체 체크포인트의 크기 한도는 아니다. 긴 판의 기록 증가·압축·호스트 선정의 회선/CPU 평가·장기 부하 검증은 후속 작업이다.

## 검증

규칙357개+서버45개, 총402개 테스트와 타입 검사·서버/클라이언트 빌드가 통과했다. 호스팅/기억 복구34개·VM 결과 집계12개·부모 IPC 정리1개 회귀는 다음을 확인한다.

- 네 모드의 이전 전후 상태·기억·RNG·후속 행동 일치와 입력 중복/누락 처리.
- 서버 틱의 계산 중단, 지정 호스트 외 전체 상태 미전달, 미확정 입력 재전송, 오래된 호스트 프레임 거절.
- 모두 이탈 후 정지/복귀, 명시적 퇴장 처리, 무응답 이전, 잘못된 상태로 체크포인트 덮어쓰기 방지, AI 전용 관전자 호스팅과 종료 콜백1회.
- 실제 WebSocket 두 참가자와 **실제 브라우저 워커 번들**을 Node worker 메시지 어댑터로 실행해 첫 호스트 종료→다음 호스트 복원→채팅 행동1회 확정/전달 확인.

추가로 Chromium 153 headless의 독립 브라우저 프로필 두 개에서 실제 웹 빌드·Worker·WebSocket을 실행했다. 새로고침·탭 종료·자리 비움 때 이전, 기존 정체로 복귀, 채팅1회 확정, 모든 호스트 이탈 뒤 재입장, AI 전용 관전자 호스팅 및 실제 기억 변경분 제출/ACK의8개 검사를 통과했고 수집한 페이지/서버 오류는0건이다. 방장 표시와 관전 화면도 캡처로 확인했다. 표준 Playwright 다운로드 실패 후 별도 Chromium 실행 파일과 한글 글꼴로 시험을 완료했다.

별도 프로세스에서 호스트 Worker를 실행하는 로컬6조건 부하 진단도 추가했다. CPU·프레임 확정 비용·통신량을 함께 기록하며 서버 틱 시간만으로 개선을 판단하지 않는다. 결과와 재현 방법은 [PLAYER_HOSTING_VALIDATION.md](PLAYER_HOSTING_VALIDATION.md)에 있다. VM 반복 진단 명령은 [PLAYER_HOST_VM_AUDIT.md](PLAYER_HOST_VM_AUDIT.md)에 있다. Node22.23.3 ARM VM 반복3회 완료 콘솔을 수신했다. 상세 원자료/해시는 아직 대조하지 않았다. 직접 P2P·모바일·실제 백그라운드 제한·원격 회선·장기 수용량은 미검증이다.

## 배포 전 확인

별도 `feat/player-host-migration` 브랜치이며 AI PR의 브랜치를 기준으로 변경을 분리한다. main과 운영 VM은 아직 변경하지 않았다. 로컬 브라우저 시험은 완료했다. VM 반복 원자료 대조와 실제 서로 다른 회선에서 이전·백그라운드 제한을 확인한 뒤 운영 반영한다. 운영 bootstrap은 이 브랜치 초안을 설치하지 않는다.

로컬에서 의존성 설치 후 루트의 `pnpm build`를 실행하고 아래처럼 시작한다. 운영 비밀키 없이 개발용 게스트 서버이며 실행 폴더의 다른 서비스와 겹치지 않는 포트를 쓴다.

```bash
PORT=8799 HOST=127.0.0.1 STATIC_DIR="$PWD/apps/client/dist" node apps/server/dist/index.js
```

같은 컴퓨터의 별도 브라우저 프로필 두 개로 `http://127.0.0.1:8799`에 접속한다. 같은 프로필의 두 탭은 같은 세션을 공유해 연결 교체가 일어나므로 두 사람 시험에는 사용하지 않는다.

AI 기억 변경분 전송의 동등성·비용·최신 부하 결과는 [PLAYER_HOST_MEMORY_DELTA.md](PLAYER_HOST_MEMORY_DELTA.md)에 있다. 기존 ARM VM 콘솔은 변경 전 소스의 결과이며 새 소스 재측정이 필요하다.
