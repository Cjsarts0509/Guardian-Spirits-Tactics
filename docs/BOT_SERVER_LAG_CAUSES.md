# 긴 이벤트 루프 지연의 원인 추적

동일 부하 재현에서는 **OS 스케줄링 대기**, **GC 정지**, **고빈도 서버 계산**을 서로 구분했다. 최초 보고의 192.94ms 한 건은 최대값만 있고 발생 시각·GC·스케줄링 기록이 없어 정확한 단일 원인을 소급 확정할 수 없다. 아래는 새 재현에서 실제로 대조한 원인이다. 운영 정책과 서버 기능은 변경하지 않았다.

## 계측과 근거

이전과 같은 실제 로컬 서버의 12봇1방/12봇씩4방/고빈도4방을 각30초 실행했다. 게임시계60배, 실제 틱250ms, 종료판 재시작, 관전 WebSocket과 HTTP health 조건을 유지했다. 검사·빌드 프로세스가 없는 상태에서 실행했다. 현재 정책은 `59ba1ef` / 원격 `7bfe0194`와 같고 실험 탐색 옵션은 계속 기본 비활성화다.

추가로 10ms 타이머의 발화 시각, 실제 서버 틱 간격, 서버/방 틱·뷰 동기화·전송·방 시작·클라이언트 처리 구간, GC 발생 시각/지속 시간을 기록했다. `/proc/self/schedstat`는 이 Node 메인 스레드의 실행/런큐 대기 누적값이고, `/sys/fs/cgroup/cpu.stat`는 CPU 할당 제한에 의한 throttling 누적값이다. 해당 파일을 읽을 수 없으면 OS 기록은 null이다. GC/OS 상태는 봇 정책·기억에 전달하지 않는다.

| 재현 구간 | 10ms 타이머 발화 간격 | 주요 관측 | 판단 |
| --- | ---: | --- | --- |
| 기본4방, 프로세스 시작 후 약32.1초 | 145.47ms | 메인 스레드 런큐 대기 **121.47ms**, 실행0.14ms, 프로세스 CPU0.08ms, GC0, throttling0, 서버 처리 구간 없음 | OS가 실행 가능한 메인 스레드에 CPU를 배정하지 못한 대기가 긴 지연의 대부분을 설명한다 |
| 기본1방, 약13.6초 | 160.53ms | 겹친 **GC154.39ms**, 메인 스레드 실행152.92ms, 프로세스 CPU156.60ms, 런큐 대기0.31ms, throttling0 | GC 작업과 일치한다 |
| 고빈도4방, 약60.5초 | 73.62ms | **서버 전체 틱67.79ms**, 메인 스레드 실행68.07ms, 런큐 대기0.02ms, 겹친 GC2.84ms | 여러 방의 동기 계산/행동 처리가 주요 원인이다 |

10ms 타이머 간격에는 정상 대기10ms도 들어간다. 기본4방의 정상 간격 초과135.47ms 중 약90%가 런큐 대기와 대응한다. `monitorEventLoopDelay`의 최대값은 각각163.05 / 145.49 / 74.78ms였다. 기본4방 전체 틱 처리 최대는5.91ms인데 실제 틱 발화 간격 최대는328.38ms였다. 따라서 **틱 처리 시간이 짧다는 사실만으로 예약된 시각에 틱이 실행됐다고 판단하면 안 된다**. 기본1방의 틱 발화 간격 최대는390.03ms, 고빈도4방은252.75ms였다.

프로세스 CPU 값은 GC/JIT 등의 다른 스레드도 합산하므로 벽시계보다 클 수 있다. OS 누적값은 파일을 읽는 시각의 표본이며 타이머 시각과 정확히 같은 순간은 아니다. 위의 주요 두 구간의 OS 읽기 비용은0.17/0.15ms로 작았다. 다른 구간에서는 계측용 읽기 자체가22.14ms 걸린 사례도 있었다. 모든 작은 스파이크를 세 가지 원인 중 하나로 강제 분류하지 않았고, 계측의 영향도 원자료에 보존했다.

## CPU 프로파일 교차 확인

OS/구간 추적을 끈 별도 실행에서 Node CPU 프로파일을 수집했다(각20초, 세조건). 가장 큰 게임 함수의 자기 샘플 가중치는 `computeAssignmentBelief` 813.80ms였고, `(garbage collector)` 가중치는211.51ms였다. 전체 약60.29초 중 idle 가중치는56.52초였다. 샘플의 시간차는 벽시계 가중치이고 실제 CPU 사용 시간이나 특정 GC 정지 길이가 아니다. 이 프로파일의 수치를 첫 재현과 직접 빼거나 성능 향상 근거로 쓰지 않는다.

프로파일은 고빈도 계산의 주요 함수와 GC 실행을 교차 확인한다. 최초193ms를 정체 배정 함수나 네트워크 직렬화 탓으로 확정하는 자료가 아니다. 프로파일 실행의 이벤트 루프 최대도123.08 / 53.08 / 160.56ms로 달라져, 단일 최대값만으로 원인을 정하면 안 됨을 보여준다.

## 수정 범위와 다음 판단

진단 드라이버에 선택적 `trace` 모드를 추가했다. 기본 모드에서는 GC/OS 추적을 시작하지 않는다. HTTP/방/전송 래퍼는 평가 서버에만 적용되며 운영 `index.ts` 번들에는 진단 코드를 넣지 않는다. 재현 원자료의 GC·처리 구간·스케줄링 정보를 PR에 보존한다.

이번에 확인한 OS 런큐 대기를 없애려고 봇 판단 규칙을 바꾸지 않았다. 로컬 공유 실행 환경의 기록만으로 Oracle VM의 CPU 부족이나 VM CPU 제한을 주장하지 않는다. 관측한 긴 구간에서 cgroup throttling 증가도 없었다. VM에서 같은 시계열을 수집하면 VM 자체의 스케줄링 대기 여부를 확인할 수 있다.

GC가 길었던 원인은 GC 작업까지 확인했지만 어떤 객체 할당이 그 정지를 유발했는지는 확정하지 않았다. 관측자·HTTP 클라이언트도 같은 프로세스이고 종료 판을 보존하므로, 운영 서버의 누수나 특정 봇 함수의 할당 문제로 단정하지 않는다. 실제 VM에서 재발하는 GC라면 별도 할당/힙 프로파일로 줄일 대상을 정한다. 고빈도 정체 배정 계산 최적화도 새로운 행동·기억 동등성 검증이 필요한 후속 작업이다.

이번 목적은 원인 구분이며 지연을 제거하거나 운영 성능이 개선됐다고 주장하지 않는다. VM은 아직 측정하지 않았고 운영 업데이트는 필요하지 않다.

## 검증과 재현

의도적인80ms CPU 작업과80ms 비CPU 동기 대기를 각각 넣는 양성대조2개 테스트에서, 지연을 해당 처리 구간과 연결하고 CPU 소모 차이를 구분했다. 전체353개 테스트(규칙332 + 서버21), 타입 검사, 서버·클라이언트 빌드 통과. 원자료 소스 SHA-256과 지연/GC/처리 구간의 시간 교차 조건을 별도 대조했다.

이전 `docs/BOT_SERVER_LOAD_AUDIT.md`의 빌드 명령으로 최신 진단 번들을 만든 뒤, 저장소 루트에서 실행한다. VM도 기존 보고서의 임시 체크아웃 명령을 사용하고 실행 인자에 `trace`를 붙인다. 서비스나 `/opt/gst/.env`는 바꾸지 않는다.

```bash
node /tmp/gst-bot-load-audit.mjs 30000 trace > docs/evaluations/server-lag-trace.json
# 별도 프로파일 실행. 위 추적 실행/검사 프로세스 종료 후 실행한다.
mkdir -p /tmp/gst-lag-profiles
node --cpu-prof --cpu-prof-dir=/tmp/gst-lag-profiles \
  --cpu-prof-name=server-load.cpuprofile /tmp/gst-bot-load-audit.mjs 20000 \
  > docs/evaluations/server-lag-profile-run.json
node apps/server/scripts/summarize-cpu-profile.mjs \
  /tmp/gst-lag-profiles/server-load.cpuprofile docs/evaluations/server-lag-profile-run.json \
  > docs/evaluations/server-lag-profile-summary.json
```

원자료는 `server-lag-trace.json`, `server-lag-profile-run.json`, `server-lag-profile-summary.json`이다. 프로파일 요약은 원본 프로파일·실행 결과·요약 스크립트의 SHA-256을 포함한다. 이전20초 부하 자료는 당시 드라이버의 역사적 결과로 유지한다.
