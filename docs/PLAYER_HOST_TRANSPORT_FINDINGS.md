# ARM VM 콘솔 수신 후 전송 구성 점검

사용자 VM은 Node22.23.3 ARM64에서6조건×3회 진단을 완료했다. 콘솔상 오류0이며 기본4방은 server/player 메인 CPU2.70/3.57%, 고빈도4방13.43/13.05%다. 기본4방/고빈도4방 메인RSS가 증가했고, 고빈도4방의 player 업로드 합계는4033.64KiB/s(약3.94MiB/s)였다. 서버 틱만 짧아졌다고 전체 자원 부담이 줄었다고 결론 내리지 않는다. [VM 결과 범위](PLAYER_HOST_VM_AUDIT.md)를 참고한다. 원자료 압축은 미수신이므로 실행별 값/해시는 직접 대조하지 않았다.

## 로컬 체크포인트 구성

`apps/server/scripts/host-payload-audit.ts`로4모드×2activity×고정2시드(123/456), 각120틱을 실행했다.12봇, 논리 틱15초(timeScale60×250ms)이며 종료되면 새 판을 시작한다. 매 틱 로그/행동 기록 추가분을 합쳐 원래 전체 상태/행동 기록과 일치하는지 대조했다(총1920프레임). [원자료](evaluations/host-payload-audit.json)에 입력·샘플 수·JSON 바이트·소스 SHA256을 보존했다.

이 자료는 로컬 고정 판의 직렬화 구성이다. VM에서 실제 전송한 프레임의 직접 증거나 CPU 프로파일/원격 네트워크 측정은 아니다. 각 필드 값의 JSON 바이트로 키/구분자는 제외한다. AI 기억은 외부 JSON에 문자열로 들어가므로 바깥 이스케이프를 포함하며, 미확정 관측 이력 비중은 그 이스케이프 전 기억 내부 바이트 기준이다.

## 다음 개선 대상

기억을 삭제/요약하면 관측 스킬·쿨다운 제약이나 이후 판단이 바뀔 수 있으므로 기존 지속 기억을 유지한 채 전송 방식만 개선해야 한다. ACK된 기억을 기준으로 변경/추가분을 전송하고 서버가 원본 기억을 조립해 이전 체크포인트를 만들도록 검토한다. 서버/방장 상태가 어긋나면 확정하지 않고 전체 체크포인트로 복구하는 경계를 확인해야 한다.

구현 시 네 모드의 복원 후 행동/RNG/기억 일치·잘못된 기준/누락/중복·호스트 이전/실브라우저 검증을 수행하고 새 고정 소스로 VM을 재측정한다. 현재는 AI 정책과 메모리/호스팅 프로토콜을 변경하지 않았다. 운영main/릴리즈/VM업데이트도 없다.

재현은 저장소의 의존성 설치 후 다음 명령이다.

```bash
cd apps/server
node --import tsx scripts/host-payload-audit.ts > /tmp/gst-host-payload.json
```

이 진단은17f8073 시점의 전체 기억 문자열 전송 방식이다. 후속으로 [AI 기억 변경분 전송](PLAYER_HOST_MEMORY_DELTA.md)을 구현했으며 기존 표/원자료를 새 방식 측정값으로 교체하지 않았다.
